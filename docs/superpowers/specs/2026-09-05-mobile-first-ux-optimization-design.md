# 餐饮保险报价器移动端 UX 优化设计规格

## 1. 文档状态

- 状态：待用户复核
- 设计确认日期：2026-09-05
- 适用范围：现有 MVP 前端的移动端体验优化
- 主要目标设备：iPhone 17 Pro、iPhone 17 Pro Max
- 设计方向：面向普通消费者的平衡紧凑型报价流程

## 2. 背景与目标

现有页面在手机上存在标题和关键数字偏大、纵向留白较多、首屏有效信息不足、员工人数录入效率偏低，以及软键盘可能遮挡输入区域等问题。

本次优化不改变报价规则、步骤条件、计算结果或数据结构。目标是让普通餐饮企业客户在手机上更快、更清楚地完成单门店报价，同时保留必要的险种解释，避免界面变成高密度后台表单。

## 3. 已确认的设计决策

1. 采用“平衡紧凑”方案：明显降低标题、卡片和留白尺寸，但不牺牲可读性与触控面积。
2. 以 iPhone 17 Pro 的约 402px CSS 宽度和 iPhone 17 Pro Max 的约 440px CSS 宽度作为主要视觉与交互测试基准。
3. 页面仍需在约 360px 宽度下无横向溢出，但不以 375px 作为主要设计画布。
4. 营业面积只使用直接数字输入，不增加常用面积快捷选项。
5. 员工人数使用“减号—可直接输入的数值—加号”组合控件。
6. 软键盘弹出时暂时收起底部固定报价栏，保证当前字段、辅助说明和错误提示可见；键盘关闭后恢复。
7. 险种解释必须直接保留在选项卡片中，但适当精简话术，不增加“了解详情”等展开交互。
8. 移动端优先，桌面端仅做内容宽度和留白增强，不维护两套不同流程。
9. 不修改 `docs/design.pen`，也不修改业务规则和结构化规则。

## 4. 响应式基准

### 4.1 主要测试视口

- iPhone 17 Pro：402px 宽；同时覆盖 Safari 浏览器工具栏展开和收起后的不同可用高度。
- iPhone 17 Pro Max：440px 宽；同时覆盖 Safari 浏览器工具栏展开和收起后的不同可用高度。
- 软键盘场景：单独验证输入聚焦后的 `VisualViewport` 高度变化，不依赖固定设备高度推测键盘状态。
- 兼容下限：约 360px 宽度下仍能完整操作，无水平滚动、裁切或控件重叠。
- 桌面端：内容保持单列，以最大宽度约束和居中留白为主。

### 4.2 移动端优先实现原则

基础样式直接面向手机编写，较宽屏幕通过 `min-width` 媒体查询增强。不能继续使用桌面尺寸作为默认值，再在 `max-width` 查询中覆盖成手机样式。

固定或吸底元素必须考虑 `env(safe-area-inset-bottom)`。页面内容底部预留空间需要由实际操作栏高度和安全区共同决定，不能依赖单一硬编码值。

## 5. 字体与信息密度

### 5.1 字号层级

- 页面主标题：24px，行高约 1.25。
- 分区标题或卡片主标签：16—18px，根据语义选用，不使用装饰性大字。
- 正文、表单输入和值：16px，避免 iOS 聚焦输入框时自动缩放。
- 辅助说明、单位、步骤计数：14px。
- 预估金额：在信息层级中突出，但移动端不使用当前过大的 40px 级显示；吸底栏金额控制在约 18—20px。

字号不随 Pro Max 设备宽度无上限放大。较宽设备主要增加舒适留白，而不是扩大文字。

### 5.2 间距层级

页面统一使用 8、12、16、24px 为主的间距层级：

- 同一控件内部：8—12px。
- 相邻字段或选择项：12—16px。
- 内容分区之间：20—24px。
- 不再使用大量 28—40px 的移动端空白。

卡片边框、圆角和内边距适度缩小，但整行点击目标和主要操作按钮的有效触控区域不得低于约 44×44px。

## 6. 页面结构

### 6.1 顶部区域

顶部品牌、步骤计数和进度条组成一个紧凑区域：

- 品牌标识尺寸缩小，不占用主要内容高度。
- 步骤计数显示为“当前步骤 / 总步骤”，总数继续根据所选险种动态计算。
- 使用细进度条表达总体进度。
- 标题之后只保留一句必要的操作引导，使首屏尽早出现第一个输入项。

### 6.2 表单主体

表单保持单列。字段使用持续可见的标签，不以 placeholder 替代标签。错误信息紧邻对应字段展示，避免用户在页面其他位置寻找错误原因。

险种和方案继续使用整行可点击卡片。卡片主标签、简短解释和选择状态在一个紧凑结构中呈现。选中状态必须同时依靠原生单选或复选控件、边框和浅色背景表达，不能只依赖颜色。

### 6.3 底部操作区

底部操作区保持稳定，只展示：

- 当前可用的预估金额或简短状态。
- 返回操作（需要时）。
- 下一步或查看报价主操作。

尚不能形成金额时不堆叠多行解释。业务原因仍在对应字段或页面主体中说明。

## 7. 输入控件设计

### 7.1 营业面积

- 使用原生数字输入框，设置适合小数的移动端输入模式。
- 输入文字不低于 16px。
- “㎡”作为固定单位显示在输入框右侧，不成为可编辑内容。
- 不提供面积快捷选项，也不提供加减按钮。
- 支持大于 0 的小数，失焦后再执行完整格式与范围反馈。

### 7.2 员工人数

每类员工使用可复用的计数输入组件：

- 左侧减号按钮、中间可编辑整数输入、右侧加号按钮。
- 加减按钮有效触控区域至少 44×44px；图标本身保持克制，避免占满按钮。
- 控件总宽度在 360px 屏幕上仍能与员工类别标签同行；空间不足时允许整行合理重排，但不横向滚动。
- 数值区域支持点击后调起数字键盘，适合一次输入较大人数。
- 值必须规范为非负整数；达到配置上限或下限时禁用对应按钮。
- 加减、直接输入、禁用和错误状态都需要明确的视觉反馈与无障碍名称。

员工分类继续来自现有配置和表单模型，不在组件中复制业务规则。

## 8. 软键盘与焦点管理

### 8.1 键盘识别

优先使用 `window.visualViewport` 监听可视区域尺寸变化，并结合当前是否存在可编辑字段焦点判断键盘状态。不能仅通过用户代理或固定高度差判断。

对于不支持 `VisualViewport` 的浏览器，使用输入聚焦和失焦作为降级信号。降级行为可以不精确识别键盘高度，但必须保证页面仍可滚动并能完成输入。

### 8.2 底栏收起

当数字输入框聚焦且软键盘使可视区域明显缩小时：

1. 底部固定报价栏临时隐藏。
2. 页面底部额外空间随之调整，避免残留大块空白。
3. 当前字段滚动到可视区域内，并为其下方错误信息保留空间。
4. 键盘关闭或输入失焦后恢复底栏。

隐藏和恢复不改变步骤、表单值或报价状态。动画保持短暂，并遵守 `prefers-reduced-motion`。

### 8.3 校验与错误焦点

- 常规校验在字段失焦或用户尝试进入下一步时触发。
- 不在用户每输入一个字符时连续显示新的错误。
- 提交当前步骤失败时，聚焦并滚动到第一个无效字段。
- 错误提示使用 `aria-describedby` 与字段关联，并使用清晰、具体的中文说明。

## 9. 险种解释文案

公众责任险、食品安全责任险和雇主责任险的解释继续直接显示，不设置详情弹层、折叠面板或额外页面。

文案遵循以下原则：

- 每个险种使用一句简短说明。
- 优先说明“保障谁、什么场景”，不重复险种名称。
- 不加入营销口号或本次报价流程不需要的保险术语。
- 不改变险种责任范围的业务含义；若现有文案涉及规则事实，精简后仍需与规则文档一致。

建议的表达方向：

- 公众责任险：顾客在店内发生意外时提供保障。
- 食品安全责任险：食品安全事故造成损失时提供保障。
- 雇主责任险：员工工作期间发生意外时提供保障。

最终实现可根据现有页面上下文微调语序，但不能进一步隐藏这些说明。

## 10. 图标与交互状态

当前用于结构和操作的 emoji、圈号、箭头或字符图标替换为现有 Phosphor 图标库中的一致图标。纯装饰图标对辅助技术隐藏；图标按钮必须有可见文本或明确的 `aria-label`。

除设计中已有的正常、悬停、选中和错误状态外，补齐：

- 键盘聚焦状态。
- 触摸按压状态。
- 禁用状态。
- 加减控件达到边界的状态。
- 键盘展开时底栏收起状态。
- `prefers-reduced-motion` 状态。

聚焦轮廓必须清晰可见，不能通过 CSS 移除后不提供替代样式。

## 11. 代码边界

本次优化集中在展示和交互层：

- 全局设计令牌与移动端优先布局样式。
- 通用进度头、底部操作栏、选择卡片和字段样式。
- 可复用员工人数计数输入组件。
- 软键盘/可视视口状态 Hook。
- 各步骤中的文案精简和控件替换。

不得改动：

- 规则 JSON 和规则版本。
- 纯 TypeScript 报价计算模块。
- 报价状态含义与金额聚合方式。
- 动态步骤的业务条件。
- `docs/design.pen`。

## 12. 测试与验收

### 12.1 自动化测试

- 员工人数加减按钮能正确更新 React Hook Form 值。
- 人数可以通过键盘直接输入，并规范为非负整数。
- 上下限时对应加减按钮禁用。
- 当前步骤校验失败时聚焦第一个错误字段。
- 输入聚焦且 `VisualViewport` 缩小时底栏隐藏，恢复后重新显示。
- 不支持 `VisualViewport` 时仍能正常输入和导航。
- 三种险种的简短解释持续可见。
- 现有报价规则、金额边界和动态步骤测试继续全部通过。

### 12.2 视觉与设备验收

至少覆盖以下场景：

- iPhone 17 Pro 竖屏，Safari 工具栏展开与收起。
- iPhone 17 Pro Max 竖屏，Safari 工具栏展开与收起。
- iPhone 17 Pro 数字键盘展开，当前输入和错误提示完整可见。
- 360px 宽度下无横向滚动或控件重叠。
- 横屏下可以完成输入和步骤导航。
- 系统字体放大后关键内容和操作仍可访问。
- 减少动态效果设置下没有必要动画。
- 桌面端单列内容宽度合理，不因放大留白而放大字体。

### 12.3 可验收结果

- 首屏比现状更早出现第一个输入项。
- 主标题、金额和卡片文字不再产生过强的视觉压迫。
- 员工人数既可快速点按调整，也可直接输入。
- 键盘不会长期遮挡当前字段、错误提示或导致底栏压住内容。
- 所有主要触控目标仍达到移动端可用尺寸。
- 报价结果与优化前保持一致。

## 13. 实施建议顺序

1. 为字号、间距、颜色、圆角和触控高度建立语义化样式令牌，并将全局布局改为移动端优先。
2. 先通过测试定义人数控件和键盘避让行为，再实现通用组件与 Hook。
3. 更新顶部进度、表单字段、险种与方案卡片、底部操作区。
4. 精简险种解释文案并替换字符图标。
5. 执行单元、组件、端到端、静态构建和多视口视觉检查。

实现期间使用小粒度英文 Git 提交，并保留所有与本次 UX 优化无关的用户改动。
