# 01 餐饮保险报价器技术选型

## 1. 文档状态

- 状态：已确认
- 日期：2026-09-01
- 阶段：MVP 开发准备

## 2. 目标与约束

### 2.1 当前目标

1. 快速交付移动端优先的五步保险报价器。
2. 首版仅提供静态前端，不依赖数据库或独立后端。
3. 报价规则在浏览器中执行，输出预估保费、不符合承保条件或人工报价状态。
4. 构建产物可部署到多个静态托管商，以便分别验证中国大陆和微信内置浏览器的可访问性。

### 2.2 后续能力

1. 保存客户联系方式、报价输入和报价结果。
2. 按员工展示不同的姓名、电话、微信等公开联系方式。
3. 提供员工及管理员登录、报价查询和员工配置后台。
4. 支持报价规则版本管理，并由服务端重新计算持久化报价。

## 3. 总体方案

采用“静态 MVP、原地升级全栈”的单项目架构：

```text
MVP
用户浏览器
  ├─ Next.js 静态页面
  ├─ 多步骤表单与本地状态
  ├─ 纯 TypeScript 报价引擎
  └─ 版本化规则 JSON

后续
用户浏览器
  ↓
Next.js 服务端接口
  ├─ 输入校验与报价重算
  ├─ 员工及管理员认证
  └─ PostgreSQL 数据库
```

前期不绑定具体托管商。项目完成后，可将同一份静态构建产物分别部署到 Vercel、Netlify、Cloudflare Pages 等平台，再对真实子域名进行大陆三网和微信实机测试。

## 4. 前端技术选型

| 领域 | 选择 | 说明 |
|---|---|---|
| 应用框架 | Next.js App Router | 支持静态导出，后续可在同一项目内启用服务端能力和管理后台 |
| 开发语言 | TypeScript | 为险种、方案、报价状态和规则版本提供强类型约束 |
| 样式方案 | Tailwind CSS + CSS Variables | 还原 Pencil 设计，并沉淀颜色、间距、圆角等语义化设计令牌 |
| 表单管理 | React Hook Form | 管理五步表单、字段状态和错误信息 |
| 数据校验 | Zod | 统一前端输入、接口请求和未来服务端校验规则 |
| 流程状态 | React Hook Form Context + `sessionStorage` | 保存步骤数据和刷新前草稿，MVP 不额外引入全局状态库 |
| 图标 | Phosphor Icons | 保持图标风格一致；不得用 Emoji 充当功能图标 |
| 包管理器 | npm | 随 Node.js 提供，减少本地开发环境的额外依赖 |

## 5. 报价引擎

报价引擎实现为无 UI、无网络、无数据库依赖的纯 TypeScript 模块。

建议目录：

```text
src/
  app/
  components/
  features/
    quote/
      calculator/
      components/
      schemas/
      types/
  config/
    quote-rules/
      mvp-1.1.json
```

统一返回结构应包含：

```ts
type QuoteResult = {
  status: "QUOTED" | "NOT_ELIGIBLE" | "MANUAL_QUOTE" | "PARTIAL_MANUAL" | "MISSING_INPUT"
  ruleVersion: string
  items: QuoteItem[]
  totalPremium: number | null
}
```

规则数据必须版本化。React 组件只负责输入和展示，不得直接包含面积系数、岗位费率或人工报价边界。

## 6. 员工专属页面

员工页面共用报价组件，通过员工标识加载公开配置：

```text
/e/[employeeSlug]
```

MVP 的员工配置可以保存在本地 JSON 中。静态导出时预生成已知员工页面；新增或修改员工后需要重新构建并部署。

后续接入数据库后，员工公开配置建议至少包含：

```ts
type EmployeePublicProfile = {
  id: string
  slug: string
  displayName: string
  phone: string
  wechat?: string
  avatarUrl?: string
  companyName?: string
  enabled: boolean
}
```

员工差异必须由数据驱动，不得为不同员工复制页面或报价逻辑。

## 7. 静态构建与托管可移植性

MVP 使用 Next.js 静态导出：

```ts
const nextConfig = {
  output: "export",
}
```

构建后生成 `out/` 目录，托管商仅负责提供 HTML、CSS、JavaScript 和静态资源。

开发期间必须遵守：

1. 不使用 Server Actions、运行时 Route Handlers 或服务端渲染。
2. 不使用 Vercel Functions、Netlify Functions 等托管商专属函数。
3. 不依赖托管商专属数据库、存储、分析或身份服务。
4. 不使用依赖服务端运行时的默认图片优化；图片在构建期处理并作为静态资源发布。
5. 字体和关键资源本地托管，不依赖中国大陆可能无法访问的第三方 CDN。
6. 为各托管商分别补充最小部署配置，但不让平台配置侵入业务代码。

候选托管商的最终选择不属于前端架构决策。项目完成后使用相同代码分别部署，并测试：

1. 中国电信、联通、移动访问情况。
2. Android 与 iOS 微信内置浏览器。
3. 首屏加载、完整报价流程和刷新恢复。
4. 微信安全提示、外置浏览器提示和分享卡片。
5. 连续多日的可用性，而非单次测速。

## 8. 数据库与管理后台演进

验证通过并开始留资后，建议使用 Supabase 提供 PostgreSQL 和 Auth，管理后台继续放在当前 Next.js 项目的 `/admin` 路由下。

建议核心表：

```text
employees
  id, slug, display_name, phone, wechat, avatar_url, enabled

quotes
  id, employee_id, rule_version, input_snapshot, result_snapshot,
  contact_name, contact_phone, consent_at, status, created_at

profiles
  id, auth_user_id, employee_id, role
```

进入该阶段后取消纯静态导出，增加服务端接口。服务端必须：

1. 使用 Zod 重新校验输入。
2. 按保存的输入和 `rule_version` 重新计算保费。
3. 不信任客户端提交的金额和报价状态。
4. 将报价绑定至来源员工。
5. 对客户个人信息设置最小权限和行级访问控制。

如数据访问显著复杂，再评估 Drizzle ORM；首个数据库版本优先使用 Supabase 类型化客户端和 SQL migrations，避免过早增加抽象层。

## 9. 测试方案

| 测试层级 | 工具 | 重点 |
|---|---|---|
| 单元测试 | Vitest | 面积档位边界、岗位费率、8 人承保门槛、金额汇总、不符合承保条件和人工报价状态 |
| 组件与流程测试 | Playwright | 五步流程、返回修改、刷新恢复、移动端交互和结果展示 |
| 实机测试 | Android/iOS 微信 | 键盘、底部安全区域、滚动、分享链接和网络可达性 |

规则调整必须同步更新结构化规则和对应测试。金额计算相关测试应覆盖边界值及文档中的已确认示例。

## 10. 暂不采用

MVP 阶段不采用：

1. Redux、Zustand 等额外全局状态库。
2. NestJS 或独立后端项目。
3. 独立管理后台仓库。
4. 微服务或消息队列。
5. 托管商专属运行时和数据服务。
6. 在客户端保存正式报价或客户个人信息。

这些能力仅在实际需求出现、且现有方案无法满足时重新评估。
